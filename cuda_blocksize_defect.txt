================================================================================
DEFECT REPORT - CUDA RELAXATION KERNEL LAUNCH CONFIGURATION
Multicore Programming 2025/2026 Exam - DuoWaves / energy_storms
File: energy_storms_cuda_core.cu
Status: CONFIRMED - affects 110 of 1440 recorded CUDA measurements
Date: 2026-08-22
================================================================================

--------------------------------------------------------------------------------
1. SUMMARY
--------------------------------------------------------------------------------

The relaxation kernel is launched with a grid size computed for a hardcoded
block width of 256 threads, while the actual block width passed to the launch
is BLOCK_SIZE, which the test suite varies from 32 to 1024.

When BLOCK_SIZE < 256 the launch provides fewer threads than the layer has
cells. The unreached portion of the layer is never relaxed, and the program
produces a wrong Result.

The campaign's correctness checking caught this: every configuration with
BLOCK_SIZE below 256 has FAIL rows, and every configuration at 256 or above
passes.

The fix is one line.


--------------------------------------------------------------------------------
2. THE DEFECT
--------------------------------------------------------------------------------

In core(), two grid sizes are computed:

    int grid_bomb = (layer_size + BLOCK_SIZE - 1) / BLOCK_SIZE;     <-- correct
    int grid_copy = (layer_size + 256 - 1) / 256;                   <-- DEFECT

Both kernels are then launched with BLOCK_SIZE threads per block:

    bomb <<<grid_bomb, BLOCK_SIZE>>> (...)
    relax<<<grid_copy, BLOCK_SIZE>>> (...)

grid_bomb is derived from BLOCK_SIZE, so blocks and threads always agree.
grid_copy is derived from the literal 256, so blocks and threads only agree
when BLOCK_SIZE happens to equal 256.

The two lines sit one after the other in the source. This is a copy-paste
slip in a single line, not a design error.


--------------------------------------------------------------------------------
3. CONSEQUENCE
--------------------------------------------------------------------------------

Total threads launched for relax() = grid_copy * BLOCK_SIZE.
Cells that must be relaxed         = layer_size.

Worked example for layer_size = 1000000 (test A_1M):

    grid_copy = (1000000 + 255) / 256 = 3907 blocks

    BLOCK_SIZE   threads launched   layer coverage
    ------------------------------------------------
            32            125024          12.50%
            64            250048          25.00%
           128            500096          50.01%
           256           1000192         100.00%
           512           2000384         100.00%   (over-provisioned)
          1024           4000768         100.00%   (over-provisioned)

BELOW 256: the tail of the layer is never written by relax(). Those cells keep
whatever value they held before the phase, so the subsequent maximum search
operates on a partially relaxed layer and returns a wrong value, a wrong
position, or both.

AT OR ABOVE 256: more threads are launched than there are cells, but the
kernel's own bounds test discards the surplus:

    if (i == 0 || i == layer_size - 1) { ... }
    else if (i < layer_size - 1) { ... }

so over-provisioning is harmless. This is why the defect is invisible at the
default block size and only appears when the suite sweeps below it.


--------------------------------------------------------------------------------
4. EVIDENCE FROM THE CAMPAIGN
--------------------------------------------------------------------------------

Correctness verdicts recorded for branch cuda-1D, 60 measurements per block
size (12 tests x 5 repetitions):

    Block size    FAIL    PASS    Predicted coverage
    ----------------------------------------------------
            32      40      20              12.5%
            64      35      25              25.0%
           128      35      25              50.0%
           256       0      60             100.0%
           512       0      60             100.0%
          1024       0      60             100.0%

The boundary sits exactly at 256, precisely where the model predicts it.

The partial passes below 256 are the small workloads. When layer_size is small
enough that the launched threads still cover the whole layer, the run is
correct despite the wrong grid size. Tests such as C_3 and A_20k fall in this
category; the large-layer tests do not.

Total affected measurements: 110 FAIL rows out of 1440 for cuda-1D. The other
three CUDA branches should be checked with the same query (see section 7).


--------------------------------------------------------------------------------
5. WHAT IS *NOT* WRONG
--------------------------------------------------------------------------------

An earlier hypothesis was that the block-size sweep never happened at all,
because the source contains:

    #define BLOCK_SIZE 256

which would override the -DBLOCK_SIZE=<n> passed by the build. If that were
happening, all six configurations would have compiled to the same binary and
the block-size study would be meaningless.

THIS IS NOT THE CASE. The suite defends against it in
scripts/suite/parallel_job.sbatch:

    ensure_block_size_guard()
    {
        local core="$WORKTREE/energy_storms_cuda_core.cu"
        if grep -q '#ifndef BLOCK_SIZE' "$core"; then
            return 0
        fi
        echo "NOTE: branch $BRANCH hardcodes BLOCK_SIZE, patching the worktree
              copy with an ifndef guard"
        sed -i 's/^#define BLOCK_SIZE 256$/#ifndef BLOCK_SIZE\n#define BLOCK_SIZE
              256\n#endif/' "$core"
        grep -q '#ifndef BLOCK_SIZE' "$core"
    }

called immediately before:

    make -C "$WORKTREE" energy_storms_cuda CUDA_EXTRA_CFLAGS="-O3 -DBLOCK_SIZE=$BLOCK_SIZE"

The guard rewrites the hardcoded #define into an #ifndef/#endif pair inside the
disposable worktree, so the command-line -D takes effect and six genuinely
different binaries are produced.

The correctness data proves the guard worked: if every binary had been compiled
at 256, every configuration would have passed. The observed failures below 256
can only occur if BLOCK_SIZE really did take the values 32, 64 and 128.

The block-size study is therefore valid. The defect is in the kernel launch,
not in the build.


--------------------------------------------------------------------------------
6. FIX
--------------------------------------------------------------------------------

One line, in core(), in energy_storms_cuda_core.cu:

  BEFORE
    int grid_copy = (layer_size + 256 - 1) / 256;

  AFTER
    int grid_copy = (layer_size + BLOCK_SIZE - 1) / BLOCK_SIZE;

This makes grid_copy consistent with grid_bomb on the line above, and blocks
and threads agree at every block size.

VERIFICATION AFTER THE FIX
Rebuild at BLOCK_SIZE=32 and confirm the Result line now matches the sequential
baseline on a large-layer test (A_1M). Before the fix that configuration fails;
after it, it must pass. This is the same before/after Result comparison used to
validate the safelen change on the hybrid side.

NOTE ON SCOPE
Check whether cuda-first, cuda-shared and main carry the same line. They are
variations on one algorithm and the defect may have been inherited.

Cost: 3 block sizes x 4 branches = 12 jobs, GPU nodes only, submitted one at a
time under MaxSubmitPU=1.
Result: a complete and correct block-size study across the full range.

OPTION 2 - FIX AND DOCUMENT, KEEP THE DATA
Apply the fix to the source, keep the campaign data as recorded, and report the

once the mechanism is documented.
Cost: writing only.
Result: an honest account in which the measurement infrastructure demonstrably
detected a real bug in the code under test. This is a point in favour of the
methodology, not against it.

OPTION 3 - RESTRICT THE STUDY TO 256 AND ABOVE
Reduce CUDA_BLOCK_SIZES to "256 512 1024" and regenerate the spreadsheet.
Cost: regeneration only.
Result: all cells pass, but the most interesting finding in the CUDA section is
removed from the report. NOT RECOMMENDED.

Options 1 and 2 are both defensible. Option 1 is stronger if time allows;
option 2 costs nothing and is still a good answer at the defence.

WHAT SHOULD NOT BE DONE

defect or explaining the FAIL cells. An examiner reading the correctness column
will ask why the three narrow block sizes fail, and the answer needs to be
prepared.

9. RELATED OBSERVATIONS IN THE SAME FILE
--------------------------------------------------------------------------------

9.1 DEBUG OUTPUT IN THE MEASURED BINARY
core() begins with:

    printf("calc_threshold: %f\n", calc_threshold);

This prints on every run of the graded binary. It does not collide with the
suite's parsers, which match "Time:" and "^Result:", but it should be removed
or guarded before submission.

9.2 GLOBAL MEMORY TRAFFIC IN THE BOMBARDMENT KERNEL
The bomb kernel accumulates directly into global memory inside the particle
loop:

    d_layer[i_layer] = d_layer[i_layer] + energy_k;

with a register-accumulator version present but commented out immediately
above. This performs a global read-modify-write per particle rather than a
single write per cell. It is a plausible target for the shared-memory branch
and should show up clearly once the CUDA phases are profiled.

Neither of these is a correctness problem. Both are worth a sentence in the
report.
