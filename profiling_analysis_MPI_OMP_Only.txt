1.3 KNOWN MEASUREMENT ARTEFACT - PHASE SUMS
The four phases are reduced with MPI_MAX INDEPENDENTLY. Different ranks can win
different phases, so their sum corresponds to no single real execution and can
exceed the measured wall time.

  Example, Add_SIMD_Directives / hyb_4n_8x4 / A_1M:
    bombardment  0.3288
    exchange     0.0108
    relaxation   0.0000
    reduction    0.0082
    ------------------
    sum          0.3478   vs measured wall time 0.3365

CONSEQUENCE: phases must be reported as proportions of the measured WALL TIME,
never as a percentage of their own sum, and the four percentages are not
required to add to 100%.

Additionally, the following are NOT covered by the timers: initial array
zeroing, memory allocation, and the final MPI_Reduce that aggregates the
timings themselves.

Exchange, relaxation and reduction together never exceed ~3% of wall time, even
at 128 ranks spread over 4 nodes.

INTERPRETATION
The nested loop over cells x particles inside the bombardment phase accounts for
essentially the entire runtime. The application is compute-bound, not
communication-bound. This is also the explanation for the high parallel
efficiency observed in the main campaign: there is very little communication
for parallel overhead to erode.

5. FINDING 4 - TWO SECONDARY OBSERVATIONS
--------------------------------------------------------------------------------

5.1 EXCHANGE COST IS HIGHER IN THE SIMD BRANCH

  4 nodes, A_1M, layout 1x1:
    immediate           exchange = 0.0114 s
    Add_SIMD_Directives exchange = 0.1088 s   (~9.5x higher)

Two explanations are consistent with the data, and the measurement cannot
separate them:

  (a) ALGORITHMIC. Add_SIMD_Directives uses blocking MPI_Sendrecv; immediate
      uses non-blocking MPI_Isend/MPI_Irecv followed by MPI_Waitall. Blocking
      calls expose imbalance as wait time.

  (b) SLACK. immediate's bombardment phase is ~2x slower, giving ranks more
      opportunity to converge before the exchange, so less imbalance surfaces
      at the communication point.

Since the exchange is at most ~3% of wall time in both branches, the effect is
not material to overall performance. It should be reported as an observation,
not as a defect, and both explanations should be stated.

A further outlier: Add_SIMD_Directives / hyb_1n_2x1 / A_1M shows exchange =
0.2583 s against ~0.003 s for comparable single-node layouts. Same mechanism -
with only two ranks the blocking Sendrecv absorbs the full imbalance.

5.2 REDUCTION COST GROWS WITH THREADS PER RANK

  Same 32 cores on one node, A_1M:
    hyb_1n_4x8 (4 ranks x 8 threads)   reduction = 0.0080 s
    hyb_1n_8x4 (8 ranks x 4 threads)   reduction = 0.0015 s   (5.3x lower)

CAUSE
After the parallel maximum search, the master thread scans threads_results[]
serially to combine per-thread results. With 8 threads per rank that scan is
twice as long, and the LocalData struct is 8 bytes, so eight entries share a
single 64-byte cache line - producing false sharing on every write.

This is the clearest candidate for the next optimization, and a concrete answer
to the question "what would you improve next".

7. METHODOLOGICAL NOTES FOR THE REPORT
--------------------------------------------------------------------------------

7.1 INSTRUMENTATION OVERHEAD
The timers are placed in the storm loop, which runs at most 10 iterations
(test B_10). Only the master thread calls MPI_Wtime. The instrumentation adds
approximately 10 OpenMP barriers per storm iteration, i.e. on the order of 100
barriers per run - sub-millisecond against runtimes of 0.0069 s to 42 s.
Overhead is negligible for all tests except C_5k, which is already below the
resolution floor.

7.2 SAFELEN VERIFICATION
The maximum-search loop in Add_SIMD_Directives carries the pragma:

    #pragma omp for simd schedule(static) safelen(4)

The loop has a loop-carried dependence (the running maximum and its position),
so safelen(4) asserts an independence that does not hold - formally undefined
behaviour.

An empirical check was performed on the cluster (job safelen_check, 4 ranks x
4 threads, A_1M, gcc with -O3 -march=znver1 -mavx2):

    unmodified   Time: 4.986813   md5 39c5ff838b1dd2a5f9063e490a140b5d
    simd removed Time: 5.036362   md5 c303c0782554c1ad4003834c738af8ce
    diff of Result lines: EMPTY (identical)

The two binaries produce identical results. The measured campaign data is
therefore unaffected. The unmodified build reproduces the campaign binary md5
exactly, confirming the provenance chain from the branch tip to the recorded
measurements.

7.3 ENVIRONMENT NOTE
OpenMPI reports that it could not create an xpmem segment and falls back to an
alternative shared-memory single-copy mechanism. This affects intra-node
transport performance and applies uniformly to every run, so it does not affect
comparability, but it is worth one sentence in the report.

7.4 REPRODUCTION
Profiled binaries were produced by copying mpi_omp_core_profiling.c over
energy_storms_mpi_omp_core.c inside a disposable git worktree, then building the
standard energy_storms_mpi_omp target with the unmodified Makefile and
student.mk flags. No branch was modified and no commit was made. The worktree
was created on shared storage so that all ranks across nodes could reach the
binary.
